# Phase 7: MVP Polish

## 目的

全ページ種別の実動作確認で見つかった分析品質と表示上の課題を、内部の構造化契約を維持しながら段階的に改善する。

## サブフェーズ

1. **7-1 Output language**: 入力ページの言語にかかわらず、ユーザー向け分析結果を日本語に統一する。
2. **7-2 Recommendation labels**: ページ種別と推奨スコアに応じてFinal Insightの推奨ラベルを変更する。
3. **7-3 Type-specific presentation**: ページ種別固有の内部キーを日本語ラベルと適切な表示形式へ変換する。

## Phase 7-1: 日本語出力

### 方針

- 英語を含むどの言語のページでも、AIが生成するユーザー向け自然言語は日本語とする。
- 企業名、サービス名、GitHubリポジトリ名、ライブラリ名、技術名、コード、URLは原文を維持する。
- 必要な短い原文引用には日本語の説明を添える。
- `pageType`や`difficulty`などのenum、JSONキー、構造化出力スキーマは変更しない。
- Tool Callingの`reason`も安全な処理ログとして日本語にする。
- 将来の多言語設定を妨げないよう、言語規則はOpenAI adapterの共通プロンプトへ集約する。

### 対象フィールド

- 分類理由
- タイトルと要約
- 重要ポイント、リスク、推奨アクション
- 不足情報
- ページ種別固有結果に含まれる説明文と配列要素
- タグ。ただし技術名・製品名は原文を許容する。
- Tool Callingの理由

### 対象外

- 取得したページ本文の翻訳・保存
- UI言語選択
- 内部キーとenumの日本語化
- 過去に保存済みの分析結果の再翻訳

既存結果は変更せず、新規分析または再分析から日本語出力規則を適用する。

### 検証

- 日本語ページと英語ページの両方で同じ構造化スキーマを通過すること。
- 英語のGitHubページでも、要約、重要ポイント、リスク、推奨アクションが日本語になること。
- 技術名、リポジトリ名、コード、URLが不自然に翻訳されないこと。
- プロンプト単体テスト、型チェック、Lint、全テスト、ビルドを通すこと。

## Phase 7-2: 推奨ラベル

### 方針

Final Insightの推奨ラベルは固定文言を使用せず、ページ種別と`recommendationScore`からUIで決定する。AIが生成する自由文には依存させず、同じ種別・同じスコアなら常に同じ表示になるようにする。

スコア帯は以下の4段階とする。

| スコア | 判定 |
| --- | --- |
| 85〜100 | 強く推奨 |
| 70〜84 | 推奨 |
| 50〜69 | 条件付きで検討 |
| 0〜49 | 優先度低め・慎重に検討 |

ページ種別ごとの行動表現は以下とする。

| ページ種別 | 行動の基準 |
| --- | --- |
| 求人・副業案件 | 応募 |
| 技術記事 | 保存・学習 |
| GitHubリポジトリ | 調査・活用 |
| 企業・サービス | 追加調査・情報収集 |
| 一般Webページ | 確認・活用 |

`recommendationScore`が未設定の場合は0点とはみなさず、スコアを`—`、ラベルを「推奨度を算出できません」と表示する。

### 検証

- 85、70、50の各境界値で期待するスコア帯へ切り替わること。
- 同じスコアでもページ種別に応じて行動表現が変わること。
- 未採点の分析を否定的な推奨として誤表示しないこと。
- 推奨ラベルの単体テスト、型チェック、Lint、全テスト、ビルドを通すこと。

## Phase 7-3: ページ種別固有結果の表示

### 方針

- DB、Zodスキーマ、OpenAI Structured Outputsでは英語の内部キーを維持する。
- UIへ渡す表示モデルの変換時に、ページ種別ごとの日本語ラベル、表示順、値の形式を適用する。
- `name`、`valueProposition`、`mainFeatures`などの内部キーを画面へ直接表示しない。
- 固有分析結果を先頭8件に制限せず、スキーマで定義された全項目を表示する。
- 配列は` / `区切り、空値は`—`として表示する。
- 0〜100の適合度・優先度は`xx / 100`、記事の難易度は「初級・中級・上級」、GitHubのテスト有無は「あり・なし・不明」とする。

この変換は表示層に限定するため、保存済みJSON、AI出力契約、Repository、マイグレーションには変更を加えない。

### ページ種別ごとの主なラベル

| ページ種別 | 表示例 |
| --- | --- |
| 求人・副業案件 | 案件タイトル、必須スキル、スキル適合度、応募推奨 |
| 技術記事 | 記事テーマ、前提知識、難易度、学習優先度 |
| GitHubリポジトリ | 技術スタック、ディレクトリ構成、テストの有無、改善候補 |
| 企業・サービス | 企業・サービス名、提供価値、想定ユーザー、差別化要素 |
| 一般Webページ | ページの目的、ユーザーにとっての有用性、信頼性に関する注意点 |

### 検証

- 全5ページ種別で英語の内部キーが画面に露出しないこと。
- 求人の18項目を含め、種別固有スキーマの全項目が表示モデルへ変換されること。
- スコア、難易度、真偽値、`null`、配列が期待する形式になること。
- 既存の保存済み分析結果にも再分析なしで表示変換が適用されること。
- 表示変換の単体テスト、型チェック、Lint、全テスト、ビルドを通すこと。
